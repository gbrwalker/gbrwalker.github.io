Fleet data platform — ingestion, orchestration and delivery

Sole author and maintainer — architecture, implementation, operation · 2026-03 to present

Python · ETL · GitHub Actions · Power Automate · CI/CD

Ingestion and orchestration of 22 datasets from 7 external sources through 9 Python pipelines, with 29 test files in continuous integration.

Architecture, decisions and outcome

The problem

Fleet operations at a distributor with four branches and around 150 vehicles depended on seven data sources that did not talk to each other: maintenance management, time-and-attendance, refuelling, safety checklists, distribution, and a corporate mailbox where preventive maintenance receipts arrived.

None of those sources delivered analysis-ready data. Some had an API, some existed only as a web portal behind a login, and some existed only as an e-mail attachment. Consolidating meant someone logging into each system, exporting a report, cleaning it by hand and pasting it into a spreadsheet — work that repeated every analysis cycle and whose output was stale the next day.

The cost is measured: one full analyst-day per analysis cycle, spent before the analysis began. Pull the report from each source, paste the raw data into the spreadsheet, clean it there, and only then look at the number. Today the data arrives dashboard-ready, refreshed up to six times a day, and the analysis starts the moment the file opens.

The repository is organised into one package per source, plus a shared package holding the storage client, the system catalogue and common utilities. Two of the 22 datasets are not external: they are derived, computed by crossing two others.

Technical decisions

  • Orchestrate with the repository's own CI, not a dedicated orchestrator. The operation has 9 pipelines with simple scheduling and no complex dependencies between them. CI already provides scheduling, on-demand runs, run history, a secret vault and notifications — free, and with no server to maintain. Alternative rejected: a dedicated orchestrator, which would bring a dependency and reprocessing interface but charge a running server and a second piece of infrastructure to watch, on a team of one.
  • Replace the data warehouse with a compressed file layer. The first version wrote to a cloud data warehouse. It moved to compressed files read directly by the BI layer. Alternative rejected: keeping the warehouse — it solved ad-hoc SQL queries, but the volume did not justify the recurring cost, and the only consumer of the data was the BI platform, which reads a file as well as it reads a table.
  • Migrate in two phases, changing one variable at a time. The next migration — moving files off the cloud and writing to a local server, read through a gateway — was deliberately split in two: first change where it runs and where it writes, keeping the file format byte-for-byte identical; only then change the format. Alternative rejected: doing both at once, which was faster on paper — and would have left three simultaneous changes with no way to know which one broke the report when something broke.
  • Browser automation for what has no API. Two sources exist only as a web portal with a login and multi-factor authentication. Rather than leaving them out, they came in through a headless browser, with the second factor resolved by reading the mailbox programmatically. Alternative rejected: periodic manual export, which is the problem this project exists to eliminate.
  • A dry-run mode before any new load. A new pipeline goes in without touching the base or the progress marker, publishing its output as an artefact for review. It reaches production only by an explicit manual trigger. Alternative rejected: ship straight and fix later — cheap until the first corruption of historical data.
  • A single system catalogue, with a deliberate side effect. Every pipeline must be registered in a central catalogue; anything not registered is dropped from the refresh log. The consequence is harsh on purpose: a forgotten pipeline disappears from the monitoring dashboard instead of showing up as stale data pretending to be fresh.
  • Dependencies pinned to exact versions, with an environment check. A script compares what is installed against what CI uses, without installing anything. The motivation was concrete: a major version difference in a data manipulation library makes the pipeline run with different semantics from production without breaking — the worst kind of defect, because it does not announce itself.
  • Weighted linear regression to estimate per-vehicle mileage. The odometer arrives from two independent sources, with missing readings and gross outliers. Instead of interpolating, a weighted line is fitted per vehicle, with outlier filtering and a weighted coefficient of determination as the confidence measure. Alternative rejected: using the last valid reading, which propagates a single typo for weeks.

Outcome

  • 22 datasets from 7 external sources consolidated by 9 production pipelines, with a full cycle every two hours, 7am to 6pm — extraction, load and dataset refresh chained with no manual step. Source: system catalogue and repository workflows, counted on 2026-08-23.
  • 88 Python modules and 29 test files running in continuous integration on every change, with a minimum coverage gate, static analysis and dependency vulnerability auditing. Source: same count.
  • 542 commits between 2026-03-06 and 2026-08-23. Source: git history.
  • One analyst-day per analysis cycle, eliminated. It was the fixed cost of preparing data before analysing it; today it is zero. Source: an account of the prior process, medium confidence.
  • The execution-time gain attributed to asynchronous processing has no source and was left out of this document: the 2026-08-23 audit of the run history found no prior period to compare against.
Full case study

A fleet data platform run by one person

The problem

A distributor with four branches operates around 150 vehicles. The information needed to manage that fleet existed — refuelling, maintenance, telemetry, checklists, driver hours — but lived in seven different external systems, each with its own idea of how to hand data over.

The process for answering any question was this: log into each system, download the report, paste it into a spreadsheet, deduplicate by hand, and only then push it to the visualisation layer. One full analyst-day, per cycle, before anyone looked at the first number. By the time the answer was ready, the question had changed.

The real problem was never a lack of data. It was that the cost of consolidating it made asking anything prohibitive — and so almost nothing was asked.

The architecture

Nine Python pipelines, orchestrated by the continuous integration platform's scheduler, consolidating 22 datasets from 7 external sources. They run every two hours through the business day. There is no server: each run is born on an ephemeral runner, does the work, and dies.

Three characteristics are worth noting because they follow from constraint, not from taste:

No server, no intermediate database. One person operates this. Every piece of infrastructure is a piece to maintain at three in the morning. An ephemeral runner plus cloud storage covers the case and asks for no maintenance.

The visualisation layer is version-controlled as text. The 16 projects live in Git in text form, not binary. That makes model and report reviewable by diff — you can see which measure changed, and revert a broken one.

Ingestion speaks three different protocols. Some systems have an API. Others only have a screen, and are scraped by headless browser. One delivers by e-mail. The ingestion layer isolates that: for the rest of the pipeline, everything becomes the same thing.

Three technical decisions, and what each one cost

1. A retroactive window per source, not global

Decision. Each source declares how many days back to reprocess. The default is 45 days; one dataset uses 15.

Why. The sources do not lie in the same way. An expense system accepts backdated entries for weeks — if you only ingest what is new, you miss a correction made yesterday to a closed month. The checklist dataset, by contrast, is edited within a much shorter window, and rescanning 45 days there means redoing the same work six times every two hours.

Trade-off. It costs configuration and surface to get wrong: N windows to justify instead of one. That cost is real and is paid for with a test per source pinning the arithmetic. What does not get paid for is the alternative — a single window is either waste or data loss, and usually both, on different sources, which makes it hard to diagnose.

2. The quality gate aborts instead of publishing with a warning

Decision. Before writing, each snapshot is compared with the last valid publication. Empty, a drop below half the previous volume, a missing required column, or blank keys above 5% raise an exception. Nothing is written. The previous file survives.

Why. A source that is down and answers with success and an empty body is not a hypothesis: it is a Tuesday. Without the gate, the pipeline would publish an empty file over a good one, and operations would open a zeroed dashboard with no idea why.

Trade-off. A false positive freezes the data until someone looks. That is the accepted cost, and it is the right side to err on: stale data is visibly stale; wrong data looks right. Whoever consumes it does not see a warning — they see the number.

What I learned afterwards. A variant of that gate saved a case I had not anticipated: when the destination file looked freshly created, publishing the incremental window over it would have overwritten the full history with a few weeks of data. Aborting was correct, and the guard existed because the rule had been written generically — "is what I am about to write plausible given what is already there?" — rather than enumerating the cases I could imagine.

3. A mandatory dry run before any new load

Decision. Every new pipeline, or one changed in anything touching writes, first runs in a mode that executes everything — authenticates, downloads, normalises, validates — and writes nothing.

Why. The expensive part of these pipelines is not the processing, it is the side effect. Reverting a published file in a layer consumed by 16 visualisation projects is manual work, and visible to everyone who depends on it.

Trade-off. It delays every change by one execution cycle. In exchange, it turns the most expensive class of error — "published the wrong thing to production" — into one that shows up beforehand.

Results, and how they were measured

Methodology first. The execution figures come from 4,108 records of the continuous integration history, between 2026-03-06 and 2026-08-26. Duration is wall-clock time of the run. Excluded were: the dependency bot, diagnostics, backfills, one-off runs, and one workflow that runs on a local runner — that one measures whether a machine was powered on, not code performance, and on its own accounted for 83% of a month's runner time. 3,687 runs remain. The comparison is the first month against the current one.

| | March | August | | |---|---|---|---| | runs per day | 8.6 | 40.1 | 4.7x | | median duration | 112s | 78s | 1.44x faster | | 90th percentile | 209s | 202s | flat | | success rate | 98.9% | 92.4% | −6.5 pp |

Throughput multiplied by 4.7 and the tail did not regress. That is the result that matters: scaling volume normally costs latency, and here p90 stayed where it was. That was deliberate — I track p90, not the mean, because it is the tail that blows a collection window.

On the mean, and why it is not in the table. Mean duration got worse over the period, from 124s to 141s. It is dragged by a few long runs and tells a story that the median and p90 contradict. I quote both ends — median and p90 — and I do not quote the mean, because a single central figure over a heavy-tailed distribution is misleading in whichever direction you use it.

And the cost, which is the most important line. Success rate fell 6.5 percentage points. More sources, more third-party integrations, more to fail. I do not treat that as noise: it is the price of the expansion and it is measured.

One detail that changes the reading: the series is not monotonic. July closed at 97.4% with 44.4 runs per day — the best of the six months. August fell to 92.4%. In other words, 6.5 points is not the fixed price of scale; there is a specific August regression I have not yet isolated.

The largest gain is the one with no number. Eliminating the analyst-day per cycle is the result that changed the operation, and its measurement is an account of the prior process corroborated by the architecture — it is not a stopwatch. I record that with medium confidence on purpose. The honest before/after ("it was a day, today the data arrives ready") is more defensible than an inflated percentage, and I do not write "100% reduction" or "8 hours a day": the old process was not eight continuous hours of work, it was a day punctuated by it.

Data quality findings the modelling exposed, all relative: 77% of maintenance spend with no work order attached; 21% of one safety dashboard's events silently dropped due to incomplete records; 30% of driver-months with checklists filled in under four minutes — below the minimum time to actually inspect a vehicle. The third became a quality rule with a minimum and maximum band.

What I would do differently

An alert on success rate, from the first month. I found the August drop by auditing history two months later. A metric that is only looked at when someone decides to audit is not being monitored — it is being remembered. It is the most expensive item on this list because it is the easiest to avoid.

A cost-of-execution dashboard. It took an audit to discover that 1.3% of runs were consuming 83% of a month's runner time — 13 runs, ten of them the same workflow, averaging 16 hours with a 24-hour ceiling, none of them succeeding. That should have been obvious the day it started.

An explicit schema contract from the start. The first sources were integrated by reading what arrived and assuming it would keep arriving. A silent column change at the source is the class of failure that cost the most diagnostic time. The quality gate covers that today, but it was added after it hurt.

Separate what is measurable from what is not, before needing the number. I spent months carrying a performance claim inherited from an old résumé which, when I went to audit it, had no "before" to compare against — the characteristic supposedly causing the gain had been in the code since the file's first commit. The number came out of everywhere. Had I instrumented the baseline before the change, I would have the real figure instead of a claim that does not survive a follow-up question.

Production and machine-downtime tracking on a live dashboard

Production manager — defined the indicator, built the flow and ran the weekly review · 2023-10 to 2024-09

Google Sheets · Looker Studio · Data Visualization · Food Manufacturing

Downtime dashboard that disproved the hidden-loss hypothesis on the floor and supported opening a third shift, worth roughly 30% more output.

Architecture, decisions and outcome

The problem

A food manufacturer ran with four teams: production and packaging, each on a day and a night shift. Every Friday there was a results meeting with the owner to review the week's gaps.

The discussion ran on memory. Everyone knew a machine had stopped, but not for how long, nor how many times, nor for which reason and how often. Without that, the meeting became opinion: each shift remembered its own problem, and the decision went to whoever argued best, not to where the loss was largest.

The underlying question was capacity: the plant could not keep up with order demand, and the backlog was growing. The hypothesis on the table was that losses were hiding in the stoppages — that more could be produced in the same time.

  is typed; nothing to export

  the screen is the agenda

The underlying decision is the simplest one and the easiest to get wrong: the data is typed once, where it happens, and the dashboard reads from there. There is no consolidation step, nobody assembling the report the night before, and therefore no diverging version in circulation.

Technical decisions

  • The shared spreadsheet as a source, not as a report. The sheet stopped being where you look at the number and became only where you type it. Whoever looks, looks at the dashboard. Alternative rejected: keeping the analysis inside the spreadsheet with a summary tab — it works until two people edit the same cell, and then nobody can say which copy is the good one.
  • A dashboard wired to the sheet, not a weekly export. The number on screen is the number that was typed, with no gap between the two. Alternative rejected: generating a report on Thursday for Friday's meeting — which is exactly what creates the "when is this data from?" question in the middle of the discussion.
  • One row per stoppage, with a mandatory reason. That is what makes it possible to sum by machine, by shift and by cause. Alternative rejected: logging only total downtime hours per day, which is faster to fill in and answers no useful question.

Outcome

  • The weekly meeting started discussing measured data instead of memory, with the dashboard refreshed the moment an entry is typed.
  • The measurement showed there was nothing to optimise. The stoppages were concentrated and necessary — maintenance, changeover, sanitation. The founding hypothesis, that hidden losses were there to recover, fell. That is the real result of this case, and it is a result: it saved the effort of chasing an efficiency that did not exist.
  • With output already at capacity, the right decision stopped being "optimise" and became "expand". The tracking supported opening a third, overnight shift, sized by the order demand and the backlog that the record had made visible.
  • Output rose by roughly 30% with the third shift. The gain came from adding capacity, not from efficiency squeezed out of the existing process — and it was the measurement that showed that efficiency was not there to be squeezed. An approximate figure, reported by the person who ran the operation, with no formal audit.

Fleet analytics layer — 16 projects under version control

Sole author — modelling, versioning, visual standard and audit · 2026-06 to present

Power BI · DAX · Dimensional Modeling · Power Query · Data Visualization

Migration of 16 dashboards from binary files to Git-versioned projects, with 325 DAX measures reviewable by text diff.

Architecture, decisions and outcome

The problem

The fleet dashboards existed as binary Power BI files, each one saved over the last. That produces three problems that only surface later: there is no history — no way to know who changed which measure, when, or why; there is no review — a binary file has no readable diff; and there is no way back — a broken measure is only recovered from the backup somebody remembered to take.

On top of that, each dashboard repeated its own transformation logic, its own table naming, and its own visual conventions. The same indicator came out differently in two reports, with nobody able to say which one was right.

The prior state is measured: analysis began by downloading a report from each system and filling a spreadsheet with raw data, which consumed one full analyst-day per cycle. Today the data arrives dashboard-ready and the analysis starts the moment the file opens.

The dashboards serve around 20 people in operations, covering a fleet of roughly 150 vehicles across four branches.

Architecture

platform file layer
    │
    ▼
shared dataflows
  one transformation, reused
  by several models
    │
    ▼
16 projects in text format
  version-controlled in Git
  semantic model + report,
  both readable and diffable
    │
    ▼
publication to workspaces
  reports by business area

Each project is a folder holding the semantic model and the report as text, not as binary. Tables follow a prefix by role — fact, dimension and calculated — and measures are centralised in their own table rather than scattered across the facts.

Technical decisions

  • Version the project as text, not the binary. This is the decision that carries all the others: model and report become readable files, with a reviewable diff, per-measure history and the ability to go back. Alternative rejected: staying on the binary and disciplining backups — that is what already existed, and it is what produced the problem.
  • Concentrate transformation in shared dataflows. Several models read the same source and each transformed it its own way. Transformation moved up into a shared layer, consumed by all of them. Alternative rejected: standardising by convention, trusting each model to repeat the same steps — which is exactly what fails silently.
  • Do not migrate the inventory model to the shared layer, and close the decision in writing. That model uses incremental refresh, which the shared layer does not support at the available licence tier. Migrating would make every refresh re-read three years of daily files against a two-hour window. Alternative rejected: migrating for consistency — the consistency would cost the executive dashboard its refresh.
  • A custom visual standard for the densest pages. Pages with many indicators are now designed as a single visual instead of dozens of native visuals stacked together. The gain was measured by Power BI's own compliance audit. Alternative rejected: staying native, which is simpler to maintain but did not deliver the requested density without degrading the audit.
  • Pin the version of the model automation tooling, and treat updates as a manual act. The tools used to edit the model load at session start, before any verification. With a floating version, each session would run whatever was published that minute, with no record and no reproducibility. The written rule rejects any version published less than 48 hours ago — the window in which a malicious publication has not yet been caught by the ecosystem. Alternative rejected: always using the latest version, which is convenient and hands the security decision to chance.
  • Automatic guards against destructive commands and secret exposure. The repository has checks that intercept dangerous operations before they run. Alternative rejected: relying on the attention of whoever is editing — which works until the tired day.
  • Measure before concluding, including about the repository itself. It is written into the project's documentation: any claim about the repository comes from reading code, history or a run, never from assumption; where it could not be measured, it says so. The rule came from a real mistake — a dashboard count table diverged from reality in three places.

Outcome

  • 16 Power BI projects version-controlled in Git, totalling 325 DAX measures, 282 tables, 98 pages and 1,004 visuals. Source: count in the repository on 2026-08-23.
  • 727 commits between 2026-06-29 and 2026-08-12. Source: git history.
  • Around 20 people consume the dashboards, covering a fleet of roughly 150 vehicles across four branches.
  • The compliance audit of one dashboard fell from 39 errors and 18 warnings to 3 errors and 5 warnings after adopting the custom visual standard; another closed at 0 errors and 6 warnings, the 6 being structural — the validator does not recognise the custom visual's identifier. Source: Power BI's own audit report.
  • Data quality findings that the modelling exposed, all relative: - 77% of maintenance spend had no work order attached — reconciliation covered only a minority of the documents. - One safety dashboard was silently dropping 21% of events, due to incomplete owner records. - 30% of driver-months had checklists filled in in under four minutes — below the minimum time to actually inspect a vehicle. Fleet cost intelligence from open data — a public pipeline

Sole author and maintainer — architecture, implementation, operation · 2026-08 to present · code on GitHub

Python · ETL · GitHub Actions · CI/CD · Data Quality

Public Python pipeline over Brazilian open fuel-price data, with a per-source retroactive window, quality gates that abort publication, and 43 tests in continuous integration behind a 60% coverage gate.

Architecture, decisions and outcome

The problem

The data engineering work I run in production is private and nobody can open it. That is a real career problem: a recruiter cannot assess what they cannot read.

This repository exists to solve that — the same engineering, on data that can be shown. It answers: what it costs to run a truck per kilometre, by state and by month, and how that cost moves against the regulated minimum freight floor.

Architecture

Two sources that mutate in different ways, and that difference is what gives the project substance:

  • ANP — weekly prices. The current semester's file is rewritten on every publication, so a week already ingested can change. This forces a retroactive window and idempotent reprocessing.
  • ANP — monthly sales. Month M closes at the end of M+1. This forces handling provisional data and its flip to final, which is a different problem.
  • ANTT — freight floor. A reference table maintained by hand.

The flow is ingest → normalize → transform → publish, with the quality gates at the publication boundary and not before. Validating early protects the processing; validating at the boundary protects the consumer — and only the second one matters when something goes wrong.

Technical decisions

A retroactive window per source, never global. Prices look back 200 days; sales, 70. A single window for different behaviours is either waste or data loss, and usually both, on different sources.

The gates abort, they do not warn. An empty snapshot, a volume drop below half, a missing key column, empty keys above 5%, a price out of range or a missing month all raise an exception and nothing is written. Bad data published is worse than stale data: whoever consumes it does not see the warning, they see the number.

Station-level detail is dropped and never republished. The raw file identifies every retailer by tax ID and street address. Aggregating to state level is a modelling decision that is also the privacy decision, and a test asserts that a tax ID from the real file never appears in the output — so it cannot regress quietly.

Outcome

  • 40 tests, 74% coverage, with a 60% gate in CI. Clean lint.
  • Runs against the live ANP servers: 22,625 fleet-fuel rows out of 72,049 downloaded, aggregated by (state, month, product).
  • Schema verified by downloading the real 3.8 MB file, not assumed from documentation. Three traps of Brazilian public data each have a test: UTF-8 with BOM (the first column vanishes silently), the ; separator, and the decimal comma that turns 6,79 into 679.
  • Idempotency in three layers — hash at ingestion, natural key at transformation, atomic write at publication — proved in tests, not asserted in the README.

Credit card fraud detection — XGBoost against SVM on an imbalanced dataset

Sole author — preprocessing, training both models, evaluation and report · coursework project · 2025-12

Python · Pandas · NumPy · Matplotlib · Machine Learning

Fraud classification over 283,726 transactions with 0.17% positives: XGBoost at 86.4% recall and 0.977 AUC-ROC against an SVM at 91.5% recall and 6,452 false positives.

Outcome and methodology

Outcome

Test set: 70,932 transactions, 118 of them fraud (0.166%).

  • XGBoost — 86.4% recall (102 of 118 frauds), 24.9% precision, F1 0.386. Confusion matrix: 70,506 true negatives, 308 false positives, 16 false negatives, 102 true positives. Threshold 0.05.
  • Tuned SVM — 91.5% recall (108 of 118 frauds), 1.6% precision, F1 0.032. Confusion matrix: 64,362 true negatives, 6,452 false positives, 10 false negatives, 108 true positives.
  • XGBoost AUC-ROC: 0.977, against 0.5 for a random classifier. That is the comparison that counts on this dataset. The notebook records in text that both models cleared 0.96 and that XGBoost reached 0.977; the SVM's exact AUC exists only inside the plot and was never printed — it sits between 0.96 and 0.977, and no closed figure can be quoted.
  • Neither model's accuracy should be quoted. XGBoost scored 99.54% and the SVM 90.89%, both below the 99.83% the majority-class baseline delivers without learning anything. It is the textbook demonstration of a metric being wrong, not of the models being bad.
  • A measured trade-off, not an opinion: the SVM catches 6 more frauds than XGBoost and charges 6,144 more false positives for it — from 308 to 6,452, a factor of 21. Each false positive is a legitimate transaction blocked or a manual review opened.

The conclusion recorded in the report alongside the notebook is to use XGBoost as the primary model and the SVM as a complementary layer during elevated-risk windows. It is a coursework recommendation: neither was ever run against real data.

Random Forest over 1,599 red wine samples: 66.0% accuracy across 6 classes against 42.5% for the majority-class baseline, and the finding that hyperparameter search bought 0.25 percentage points.

Outcome and methodology

Outcome

  • Version 1, 6 classes — 66.0% accuracy, against 42.5% for the majority-class baseline. A 23.5 percentage-point gain. Classes 5 and 6 carry the number: F1 of 0.74 and 0.66. Classes 3 and 4 came out with precision and recall of zero — the model never predicts them; class 8 got 1 of the 5 test samples right (precision 0.50, recall 0.20, F1 0.29). Macro F1 of 0.36 against weighted F1 of 0.64: the gap between the two is the measure of the imbalance.
  • Hyperparameter search — 66.25% accuracy, a 0.25 percentage-point gain over the 66.0% of the default model, after 50 combinations sampled from a grid of 1,800 with 3-fold cross-validation. The rare classes did not move: 3 and 4 stayed at zero and class 8 kept its single hit. It is the most useful result of the exercise: it measures that the problem was never in the hyperparameters.
  • Version 2, 3 classes — 87.5% accuracy, against 82.5% for the majority-class baseline. The jump from 66% to 87.5% looks large and is not: the problem changed. Against the correct baseline the gain is 5 percentage points, 4.7 times smaller than the 23.5 of the 6-class version. Comparing 87.5% with 66.0% would be comparing a 6-choice test with a 3-choice one.
  • The "poor" class stayed invisible. Of the 16 poor samples in the test set, none was predicted — all were classified as average. Macro F1 of 0.53. Regrouping hid the imbalance; it did not solve it.

The finding that holds is worth more than the metric: the gain came from reframing the target and from accepting that, with 10 and 18 samples, no hyperparameter teaches the extreme classes.
